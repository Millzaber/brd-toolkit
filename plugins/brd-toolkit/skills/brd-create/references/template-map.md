# ผลการศึกษา Mini BRD Master

ต้นฉบับ: assets/mini-brd-master.docx ซึ่งเก็บเนื้อหาเดิมไว้เป็นแหล่งอ้างอิง ห้ามนำข้อเท็จจริงของงานตัวอย่างไปใช้กับงานใหม่

## รูปแบบคงที่

- A4 แนวตั้ง 21 × 29.7 ซม. หนึ่ง section ระยะขอบทั้งสี่ 2.54 ซม.
- body runs ทั้งหมดที่ตรวจพบใช้ TH SarabunPSK 14 pt ชื่อเอกสารอยู่กึ่งกลาง ตัวหนาและขีดเส้นใต้ตามต้นฉบับ หัวข้อและ label เป็นตัวหนา เนื้อหาปกติ มีการเน้นบางคำในงานตัวอย่างซึ่งไม่ใช่ข้อกำหนดให้เน้นคำนั้นในทุกงาน
- มีโลโก้ Pojjaman และ BUILKONE ส่วนหัว ต้องคงภาพ ขนาด และตำแหน่งจากต้นฉบับ
- ท้ายกระดาษซ้าย `PJM_BRD_REV_00-26` ขวา `Page X of Y` ใช้ field เดิม ไม่แทนเป็นเลขคงที่
- label ไทย–อังกฤษตามต้นฉบับ รวมถึง `ชื่อบริษัท (Project Name)` ซึ่งภาษาอังกฤษไม่ตรงกับความหมายไทย: กรอกชื่อบริษัทและคง label เดิมไว้ เว้นแต่ผู้ใช้ขอแก้
- รายการข้อมูลส่วน 1–2 มี bullet จาก numbering ของ Word รายการ scope ใช้ขีดและการเยื้อง FR/AC เป็นรายการเรียงรหัส
- ตารางอนุมัติ 4 แถว × 4 คอลัมน์: บทบาท | ช่องลงนาม | วันที่ (Date) | ช่องวันที่ ต้องคงเส้นตารางและขนาดคอลัมน์
- เรนเดอร์ต้นฉบับได้ 2 หน้าเมื่อ fontconfig เห็นฟอนต์ไทย จำนวนหน้าเป็นผลจากข้อมูล ไม่ใช่ข้อจำกัดของเอกสารใหม่

## แผนที่เนื้อหา

เลข P ด้านล่างคือ index ของ Document.paragraphs (zero-based) จากต้นฉบับ ใช้เป็นหลักฐานการตรวจตำแหน่งเท่านั้น ในการแก้ไขให้ค้นหัวข้อ/label และตรวจบริบทก่อน เพราะ index เปลี่ยนได้เมื่อเพิ่มรายการ

| ตำแหน่งต้นฉบับ | เนื้อหา | วิธีกรอก |
|---|---|---|
| P0 | เอกสาร Business Requirement Document (BRD) | คงเดิม |
| P1 | 1. การควบคุมเอกสาร (Document Control) | คงเดิม |
| P2–4 | Reference Change Request No., Created By, Requested Date | เลข CR ผู้จัดทำ วันที่ของงานใหม่ |
| P5 | 2. ภาพรวมโครงการ (Project Overview) | คงเดิม |
| P6 | ชื่อบริษัท (Project Name) | ชื่อบริษัทลูกค้า |
| P7 | เรื่องที่ต้องการ (Requested Topic) | สรุปการเปลี่ยนแปลงสั้นและชัด |
| P8 | ชื่อ Menu/ Feature/ API/ Form/ Report ที่เกี่ยวข้อง | ชื่อรายการจริง อ้าง catalog เมื่อมี |
| P9 | ผู้รับผิดชอบทางธุรกิจ (Business Owner) ฝั่งลูกค้า | ผู้รับผิดชอบที่ยืนยัน ไม่เดาจากชื่อผู้ติดต่อ |
| P10 | วัตถุประสงค์ (Objective) | ปัญหา เหตุผล และผลลัพธ์ทางธุรกิจ |
| P11 | 3. ขอบเขตการดำเนินงาน (Scope of Work) พร้อมข้อความในย่อหน้าเดียวกัน | คงหัวข้อ แทนเนื้อหาสรุปงาน |
| P12–13 | 3.1. ในขอบเขต (In Scope) และรายการ | ขอบเขตข้อมูล/งาน/เงื่อนไขที่รวม |
| P14–15 | 3.2. นอกขอบเขต (Out of Scope) และรายการ | สิ่งที่ผู้ใช้ระบุว่าไม่รวม |
| P16–19 | 4. Requirements, 4.1. Functional Requirements และ FR | รหัส FR ต่อเนื่อง ปรับจำนวนได้ |
| P20–22 | 4.2. Acceptance Criteria และ AC | รหัส AC ต่อเนื่อง ตรวจวัดผลได้ |
| P23–25 | ช่องว่างก่อนอนุมัติ | ใช้เท่าที่จำเป็นต่อรูปแบบและพื้นที่ลงนาม |
| P26 และตารางแรก | 5. การอนุมัติ (Approval) | คงบทบาททั้ง 4 ไม่สร้างลายเซ็น |

## ข้อเท็จจริงตัวอย่างที่ต้องเปลี่ยน

เลข PJMCR260920, ผู้จัดทำ ธนายุส แสงฉาย, วันที่ 28/09/26, บริษัท ซีซีเค พร็อพเพอร์ตี้ จำกัด, Business Owner จิราภา อินทร์ทอง, Materials, RBSO.27.001, ทีวี 55 นิ้ว และเงื่อนไข Serial → NoneStock เป็นข้อมูลของตัวอย่างเท่านั้น

ตัวอย่างกล่าวถึงทั้ง “ไม่มี Serial” และ “ไม่เกิด Stock” ซึ่งเป็นผลคนละอย่าง อย่าเหมารวมเป็นข้อกำหนดเดียว หากงานจริงมีความคลุมเครือต้องแยกคำถามเรื่องสถานะ Stock, Serial และข้อมูลย้อนหลังตามบริบท
