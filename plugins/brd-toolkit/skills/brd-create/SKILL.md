# BRD Create

สร้าง DOCX จาก [ต้นฉบับ](assets/mini-brd-master.docx) โดยเก็บหัวข้อ ลำดับ โลโก้ ตารางอนุมัติ และท้ายกระดาษเดิม ใช้ TH SarabunPSK 14 pt ผู้ใช้ไม่จำเป็นต้องรู้วิธีเขียน FR/AC

## เริ่มสนทนา

- หากมีเรื่องเล่าหรือข้อมูลอยู่แล้ว ให้แยกเข้าหัวข้อทันที ไม่เริ่มถามใหม่ทั้งหมด
- หากเรียกสกิลเปล่า ๆ ให้แสดงแบบรับข้อมูลครบทุกหัวข้อตาม [intake.md](references/intake.md) และบอกว่า “กรอกตามหัวข้อ หรือเล่าได้เลยว่าลูกค้าชื่ออะไร บริษัทอะไร ต้องการทำอะไร และเกี่ยวข้องกับเมนูไหน ข้อมูลที่ยังไม่ทราบเว้นไว้ได้”
- หากต้องการถามทีละหัวข้อ ให้เริ่มจากบริษัท ผู้ติดต่อ ความต้องการ และเมนู แล้วไล่ส่วนที่เหลือ แสดงภาพรวมหัวข้อให้ทราบก่อน ไม่ถามหลายสิบคำถามในครั้งเดียว
- ต้องทราบผู้จัดทำก่อนสร้างเอกสาร หากผู้ใช้ยังไม่บอก ให้ถามว่า “ใครคือผู้จัดทำเอกสาร?”
- หากผู้ใช้ไม่ระบุวันที่จัดทำ ให้ใช้วันที่ปัจจุบันตามเขตเวลาของผู้ใช้โดยอัตโนมัติ และแจ้งสั้น ๆ ว่าใช้วันที่ใด ไม่ต้องถามซ้ำ
- ตอบในแชตให้สั้น ถามเฉพาะข้อมูลที่จำเป็น รวมคำถามที่เกี่ยวข้องไว้ในข้อความเดียว
- ใช้ภาษาไทย คงชื่อเมนู ฟิลด์ API รหัสข้อมูล และคำเทคนิคตามผู้ใช้

## จัดข้อมูลและเติมช่องว่าง

อ่าน [template-map.md](references/template-map.md) เพื่อแยกส่วนคงที่จากข้อมูลเปลี่ยนตามงาน และอ่าน [menu-catalog.md](references/menu-catalog.md) เมื่อจัดชื่อเมนู

1. จัดข้อมูลเข้า 1, 2, 3, 3.1, 3.2, 4, 4.1, 4.2, 5 ให้ครบ ไม่เพิ่มหัวข้อหลักนอกแบบฟอร์มเอง
2. แยกปัญหาปัจจุบัน ผลลัพธ์ที่ต้องการ ขอบเขต และสิ่งที่ไม่ทำ ชื่อลูกค้าที่ติดต่อไม่เท่ากับ Business Owner หรือผู้มีอำนาจลงนามโดยอัตโนมัติ
3. สรุปสิ่งที่เข้าใจและถามเฉพาะข้อมูลสำคัญที่ขาดหรือขัดกัน รวมคำถามเป็นชุดสั้น ๆ โดยเฉพาะผลต่อข้อมูลย้อนหลัง ขอบเขตรหัส/บริษัท/โครงการ และสิทธิ์ผู้ใช้เมื่อเกี่ยวข้อง ห้ามนำตัวอย่าง Stock/Serial ไปบังคับใช้กับทุกเรื่อง
4. ช่วยร่าง FR-01, FR-02… เป็นพฤติกรรมที่ระบบต้องทำ หนึ่งข้อหนึ่งประเด็น และ AC-01, AC-02… เป็นผลที่ตรวจสอบได้ ครอบคลุม FR ทุกข้อ เชื่อม AC กับ FR ในข้อความได้โดยไม่เพิ่มตารางใหม่ จำนวนข้อขึ้นกับงาน ไม่จำกัดที่ 2 ข้อเหมือนตัวอย่าง
5. เรียบเรียงสิ่งที่อนุมานได้โดยตรงจากเรื่องเล่าได้ แต่เงื่อนไขธุรกิจใหม่ สิทธิ์ อัตรา ระยะเวลา และผลย้อนหลังที่ผู้ใช้ไม่ได้บอก ให้เสนอแยกในแชตหรือถามก่อน ห้ามเขียนเป็นข้อเท็จจริงที่ตกลงแล้ว
6. ห้ามใช้ชื่อบริษัท บุคคล เลข CR วันที่ รหัสไอเทม หรือ Materials จากเอกสารตัวอย่างเป็นค่าเริ่มต้น ห้ามสร้างเลข CR หรือวันอนุมัติเอง
7. ให้เขียน Out of Scope อย่างครอบคลุมจากขอบเขตที่ตกลง โดยพิจารณาอย่างน้อย เมนู/รายงานอื่น การแก้ข้อมูลย้อนหลัง สิทธิ์ผู้ใช้ สูตรหรือแหล่งข้อมูล การส่งออก/การเชื่อมต่อ และบริษัท/โครงการอื่น เฉพาะด้านที่เกี่ยวข้องกับงาน ห้ามเติมข้อจำกัดที่ผู้ใช้ไม่ได้ตกลง หากจุดใดมีผลต่อขอบเขตแต่ยังไม่ชัด ให้ถามก่อนสร้างเอกสาร
8. ก่อนสร้างเอกสาร ตรวจทุกค่าที่จะกลายเป็น `[รอข้อมูล: …]` แล้วถามผู้ใช้ให้ตอบเป็นชุดสั้น ๆ ห้ามสร้าง DOCX ที่มี `[รอข้อมูล: …]` โดยไม่เปิดโอกาสให้ตอบก่อน หากผู้ใช้ยืนยันให้ร่างต่อทั้งที่ยังไม่มีข้อมูล จึงคง placeholder ได้และแจ้งเฉพาะรายการที่ยังขาด

## สร้างเอกสาร

ใช้เครื่องมือสร้างและแก้ไข DOCX ที่มีในระบบ หากมีสกิล Documents ให้ใช้สกิลนั้น มิฉะนั้นใช้ python-docx/OOXML และ LibreOffice ตาม [document-workflow.md](references/document-workflow.md) โดยต้นฉบับนี้เป็นข้อกำหนดด้านรูปแบบเหนือรูปแบบเอกสารทั่วไป

- เริ่มจากสำเนาต้นฉบับเสมอ เปลี่ยนเฉพาะข้อมูลของงาน ห้ามแก้ไฟล์ใน assets
- ใส่ FR/AC และรายการขอบเขตได้ตามจำนวนจริง ไม่ตัดข้อมูลเพื่อบังคับให้เหลือสองหน้า
- เนื้อหาภายใต้หัวข้อต้องเป็นตัวปกติ ไม่ทำตัวหนาทั้งย่อหน้า ใช้ตัวหนาเฉพาะหัวข้อ ป้ายกำกับ รหัส FR/AC และคำหรือเงื่อนไขสำคัญที่ต้องเน้น โดยให้ส่วนที่เน้นเห็นแตกต่างชัดเจน
- เก็บแถวอนุมัติทั้ง 4 แถว ชื่อผู้ลงนามและวันที่เว้นว่างจนผู้ใช้ให้ข้อมูล การพิมพ์ชื่อไม่ใช่การลงนามหรือยืนยันอนุมัติ
- ตรวจข้อความตัวอย่างตกค้าง ความครบหัวข้อ ความสอดคล้องของขอบเขต–FR–AC ฟอนต์และเลขหน้า แล้ว render และดูทุกหน้าก่อนส่ง
- ส่ง DOCX ที่แก้ไขได้ ตั้งชื่อ `BRD_<บริษัท>_<เรื่องย่อ>.docx` ด้วยชื่อไฟล์ที่ปลอดภัย ไม่เขียนทับไฟล์เดิมโดยไม่ได้รับคำสั่ง สรุปข้อมูลที่ยังขาดสั้น ๆ นอกเอกสาร

## เมื่อผู้ใช้เพิ่มรายการเมนู

ปรับเฉพาะ references/menu-catalog.md ตามข้อมูลที่ให้ เก็บชื่อทางการ alias ประเภท และ module/path เท่าที่ทราบ ไม่สร้างเมนูจากความคุ้นเคย หากหลายเมนูตรงกันให้ถามจุดต่าง และหากไม่พบให้เก็บชื่อที่ผู้ใช้ระบุพร้อมสถานะรอยืนยันในแชต สกิลต้องทำงานต่อได้แม้รายการเมนูยังว่าง
